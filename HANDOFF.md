## A. Project goal and working style

VD Scheduler & Payroll is a Supabase-backed scheduling / rota / payroll app for a ski-resort delivery-driver operation (resorts: Crans-Montana, Zermatt, Verbier). Two roles: **manager** (configures resorts, shifts and payroll rules; sees availability; builds the weekly rota by hand or with Auto-Rota; publishes it) and **driver** (answers weekly availability; sees their own published rota).

**Stack:** React 18 + TypeScript + Vite 5, TanStack Query, Supabase (Postgres + Auth + RLS + RPC + PostgREST), vitest 2 + Testing Library (jsdom). `src/repositories/index.ts` is the single factory that picks the **mock** or **Supabase** provider from `VITE_DATA_PROVIDER` (`.env.local`, gitignored).

**How the user works (replicate it):** a strict sequence of numbered checkpoints. Architecture review (report only) → explicit approval/amendments → implementation checkpoint with a detailed spec and a numbered stop-report → each ends with "DO NOT BEGIN X". Every checkpoint: full DB + frontend regression, a real-Supabase browser walkthrough for anything RLS/trigger/multi-role-sensitive, docs (`docs/business-rules.md`, `docs/db-testing.md`, this file), one isolated commit, report, **stop**. Typical build: **PB-A DB/security foundation → PB-B repository + mock → PB-C UI → PB-D final verification + handoff** (Publish Rota followed exactly this; Auto-Rota was AR-A…AR-D).

**Standing rules:** never edit a committed migration (append-only; add a new one); never hand-edit `src/types/database.generated.ts` (`npm run db:types`); don't open PRs automatically; don't commit iCloud/filesystem workarounds or scratch scripts/fixtures; commit messages end with the `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>` line; `.env.local` must end every session as `VITE_DATA_PROVIDER=mock`; there is no hosted/linked Supabase project (local only).

## B. Manager features (live)

- **Configuration** → Drivers (create/edit/deactivate, preferred language), **Resorts** (create/deactivate/reactivate; deactivation blocked while anything operational depends on it), **Resort & Shift Setup** (one manager-facing "Shift": name, start/end, weekdays, effective period, required drivers; refresh/cancel previews), **Payroll Rules** (shift base pay + per-driver delivery rate, effective-dated, Change vs Correct — rates only, §G).
- **Rota & Availability** (`#/manager/rota`): one resort selector + one week navigator shared by two live panels — the **Manual Rota** card (assign / remove drivers on real shift instances, coverage pills, historical/published handling, and the header actions **[Generate Rota] [Publish Rota]**; §F, §F3, §F4) and the **Availability** panel (per-driver status and per-shift answers, read-only, shows "Rota published / Locked" once the week is published). The Draft / Published chip beside the week navigator is the authority for publication state.
- **Still Stage 1.1 mock:** the manager **Dashboard** and **Payroll** page (§K).

## C. Driver features

- **Availability** (`#/driver/availability`, live): answer each shift independently, partial save, explicit Confirm / Reopen (this "Reopen availability" is the driver reopening their own answers **before** publication — it is unrelated to un-publishing a rota), publication lock enforced by RLS ("Availability locked — your rota for this week has been published"), "Needs reconfirmation" after a real change (§E trigger).
- **My Rota** (`#/driver/my-rota`, live): the driver's own **published** shifts for one Monday–Sunday week, read-only; distinguishes "not published yet" / "no rota was published" (past) / "published, nothing for you" / published with shifts; refetches on mount, week change and focus. A manager's edit to a published week shows on the next refetch (no snapshot). Details §F2.

## D. Shift model

Manager-facing concept is a single **Shift** (stable `shift_types` identity + per-weekday `shift_templates` rows, Monday=0…Sunday=6). `required_drivers` lives on the Shift (mandatory, `>= 1`); a different staffing need is a separately-named Shift ("Dinner (1P)" vs "Dinner (2P)"). `materialise_shift_instances` snapshots times and `required_drivers` onto `shift_instances` (no rate/financial data on instances). `unique(resort, shift_type, date)`: two shifts on one day need two Shift types (e.g. Lunch and Dinner). Several shifts per day are normal and nothing may hard-code Lunch/Dinner or parse "(1P)/(2P)". `is_premium` is an inert legacy column — no UI, do not resurrect.

## E. Availability model

One answer per (driver, shift_instance): `available` / `unavailable` — **no row = Not Submitted** (never stored). Per-week confirmation lives in `availability_submissions`; **publication locks driver edits at the database** (the lock derives only from a currently-published `rota_publications` row). The load-bearing trigger `shift_instances_reopen_stale_confirmations()` reopens a confirmed week **only** for `shift_added`, `shift_reinstated`, `shift_time_changed` — never for `required_drivers`, name, pay, or cancellation changes. Do not weaken it. Publishing never mutates an availability answer.

## F. Manual Rota (complete — MR-A → MR-D)

## F3. Auto-Rota (complete — AR-A → AR-D)

**Architecture: the planner proposes, the database decides.** A pure TypeScript planner chooses WHO fills each open position; one atomic SQL RPC re-validates every proposed pair under a lock and applies all or nothing. The fairness algorithm exists ONLY in TypeScript (so SQL and TS cannot drift); SQL enforces only safety invariants, so a disagreement can only cause a rejection, never an unsafe write.

- **Planner** (`lib/autoRotaPlanner.ts`, pure, no I/O/clock/randomness): `buildAutoRotaPlan({ week: ManagerWeekRota, operationalToday }) → AutoRotaPlan`. Eligible = active candidate, availability for that exact shift `available`, not already assigned (Unavailable / Not Submitted never; no override). Active existing assignments (manual or auto, incl. a manual override) are preserved, count toward coverage and fairness; inactive ones count toward neither. `openSlots = max(required − active, 0)`; never over-assigns; a driver at most once per shift. **Weekend (Fri–Sun) bucket first, then weekday (Mon–Thu)**; per slot the winner has the fewest assignments in that bucket → fewest in total → **weekly tie-break = FNV-1a 32-bit of `${weekStart}:${driverId}`** (`lib/autoRotaHash.ts`, fixed test vectors) → `driverId`. Within a bucket the **most constrained shift goes first**, then date, sortOrder, startTime, name, id. Past shifts are skipped, today is eligible; past assignments still seed the counters. No overlap, daily-maximum or rest rules (§K). Greedy heuristic, not a global optimum.
- **Apply RPC** (migration `20261019110000_auto_rota_apply.sql`): `apply_auto_rota(resort, week, plan jsonb) → (resort_id, week_start, assigned_count, remaining_open_slots, uncovered_shift_ids, skipped_past_shift_count, run_id)`. Manager-only SECURITY DEFINER; the plan is **untrusted** (`[{shift_instance_id, driver_id}]` and nothing else). Under the lock it rejects a published week (`55006 published_week`), a wholly past week (`historical_week`), a past shift (`historical_shift`), and re-validates EVERY pair. Malformed → `22023`; a plan the current state no longer permits → **`VD002` `stale_plan`** (nothing written). Rows are inserted as `assignment_source = 'auto'` with audit context `{operation: 'auto_rota', run_id, …}`. The result is computed from the DB after the insert.
- **Concurrency:** one transaction advisory lock per resort + week (`rota_week_lock`; keys = the resort UUID's four 32-bit words XOR-ed, and days since 2000-01-01) taken by `apply_auto_rota`, `assign_driver`, `unassign_driver`, **`publish_rota`** and a trigger on every `rota_publications` insert/update/delete. The apply also row-locks (`FOR SHARE`) the planned shifts, drivers and availability rows.
- **Repository** `RotaRepository.generateAutoRota({ resortId, weekStart }) → AutoRotaResult` (both providers): read the week → plan → ONE apply call → return the **database's** result. `stale_plan` / `historical_shift` triggers exactly one re-read and re-plan (`autoRotaOrchestration.ts`, shared). Typed `AutoRotaError` kinds: `published_week`, `historical_week`, `historical_shift`, `stale_plan`, `permission_denied`, `resort_not_found`, `invalid_week`, `invalid_plan`, `unknown`.
- **UI** (`ManualRotaPanel` header, `components/rota/autoRotaUi.ts`): **Generate Rota** (secondary button); enabled for an unpublished week with a shift today or later; disabled with a visible, `aria-describedby`-linked reason for published / wholly historical / no-shift weeks, and while a Publish call runs. One confirmation dialog naming the resort and week — **no preview**. Notices come from the authoritative result; partial coverage is a success.

## F4. Publish Rota (complete — PB-A → PB-D)

**Architecture: the database is the only authority; React and the repository never count coverage or write the publication.** Publishing is one deliberate, server-validated act per resort + Monday–Sunday week that (a) makes the week's assigned shifts visible to drivers, (b) locks driver Availability and (c) stops Auto-Rota — all three already derive from a currently-published `rota_publications` row (`published_at is not null and unpublished_at is null`), so publishing is a single row write. **Nothing is snapshotted**: drivers read live assignments through the safe views.

- **DB (PB-A, migration `20261026100000_publish_rota.sql`, tests `87_publish_rota.sql`, 90 assertions):** `publish_rota(p_resort_id, p_week_start, p_confirm_uncovered default false) → (resort_id, week_start, published_at, uncovered_slots, already_published)`. Manager-only SECURITY DEFINER; **the only application write path to `rota_publications`** (managers keep SELECT; direct INSERT/UPDATE/DELETE revoked and the old FOR ALL policy dropped; drivers have no access; anon none). Order: shape (`22023`) → resort exists (`P0002`) → **`rota_week_lock`** → inactive resort (`23514` DETAIL `resort_inactive`) → **already published ⇒ idempotent success** (`already_published`, no write, no audit, original `published_at`) → wholly past week or no active shift dated today or later (`55006` `historical_week`) → no active shift (`23514` `no_shifts`) → **uncovered acknowledgement** → write. Uncovered = today/future ACTIVE shifts, `required_drivers` minus ACTIVE drivers' assignments, never negative, past gaps ignored (same `_auto_rota_open_slots` as Auto-Rota), **recomputed under the lock on every call**; without `p_confirm_uncovered` the server raises **`VD003`** with the count in DETAIL and writes nothing. `generation_source` is **derived by the server** (`auto` if any assignment in that resort + week is auto, else `manual`; zero assignments ⇒ `manual`; recomputed on republish) and is never supplied by the caller or shown in any UI. A retracted row (`unpublished_at` set) is republished by UPDATE (the table is unique per resort + week). Audit context: `{operation: 'publish_rota', resort_id, week_start, uncovered_slots, confirmed_uncovered, generation_source, republished}` (`confirmed_uncovered` is true only when positions were open AND acknowledged). **Publish-only: there is no unpublish / retract RPC or control** (the `unpublished_at` column semantics remain for future use and tests).
- **Repository (PB-B):** `RotaRepository.publishRota({ resortId, weekStart, confirmUncovered? }) → PublishRotaResult { resortId, weekStart, publishedAt, uncoveredSlots, alreadyPublished }` (no generation source / actor / row id). Supabase: exactly one `publish_rota` call, mapped in `supabase/mappers.ts`. Typed errors: **`PublishRotaConfirmationRequiredError`** (`uncoveredSlots`, parsed strictly from the `VD003` DETAIL — an invalid/missing count becomes `unknown`, never a made-up number; guard `isPublishRotaConfirmationRequired`) and **`PublishRotaError`** kinds `historical_week`, `no_shifts`, `resort_inactive`, `resort_not_found`, `invalid_week`, `permission_denied`, `unknown` (guard `isPublishRotaError`; mapping only in `supabase/rotaErrors.ts`). Already published is a normal result. The mock mirrors the same guards, order, recount-on-confirm and idempotency over `mockRotaPublications` (so a mock publish drives the manager rota, My Rota, the Availability lock and the Auto-Rota block); it has no lock/concurrency; a mock row may carry an internal `generationSource`.
- **UI (PB-C/PB-D):** `[Generate Rota] [Publish Rota]` in the Manual Rota header — **Publish primary, Generate secondary**. Files: `components/rota/publishRotaUi.ts` (pure enable/reason/wording rules), `PublishRotaDialog.tsx`, `usePublishRota.ts` (selection-scoped lifecycle), wired in `ManualRotaPanel.tsx`. Publish is enabled only for a loaded, unpublished week with a shift dated today or later; disabled with visible linked reasons for published ("Published", "This rota has already been published."), no shifts, wholly past; also disabled while a Publish/Generate call runs. First call `confirmUncovered: false` → on `VD003` the SAME dialog swaps to "N position(s) still uncovered" (the server's count; plus "No drivers are assigned yet." when the loaded week has no active assignment) with **Publish anyway** (`confirmUncovered: true`); the confirmed result is authoritative (no third prompt; an uncovered publish is a warning-toned notice, never an error). Already-published ⇒ success notice + refetch. Pending: buttons disabled, "Publishing…", double-submit blocked. Changing resort/week closes the dialog and drops a late result. Typed errors show first-party copy inline (alert). After success: refresh `managerRotaKeys.week` plus the Availability summary (`availabilityKeys.managerSummary`) and per-driver detail queries for that week (`availabilityKeys`); nothing else, no cross-session driver cache. **Focus** moves to the result notice after a successful publish (the opener is then the disabled "Published" control); Cancel / Escape / a failed publish return focus to the Publish Rota button. After publishing: Generate is disabled, **manual Assign and Remove stay available** and never unpublish.
- **Verified end to end (PB-D, real Supabase + mock + 375px):** see `docs/business-rules.md` §S for the full list (covered / uncovered / race / zero-assignment / zero-shift / historical / partially historical / today / inactive / idempotent / republish / generation source / driver visibility / post-publish edits / Auto-Rota block / Availability lock / direct-write security / five two-connection races / audit / mobile / accessibility).

**The weekly workflow**
- **Draft:** drivers submit and confirm Availability → manager **Generates** (Auto-Rota fills open positions with Available drivers) → manager reviews and edits with Manual Rota (override dialog for Unavailable / Not Submitted) → manager **Publishes**.
- **Published:** drivers see their own assignments in My Rota (live) · driver Availability is locked at the database · Auto-Rota is blocked (UI disabled, server `published_week`) · the manager can still edit assignments in Manual Rota (today and future shifts) and drivers see the edits on refetch · there is no unpublish.

## H. Database / RLS / RPC conventions

- Every table RLS-enabled + FORCE. **RLS is the real security boundary**; manager policies `is_active_manager()`-gated, driver policies own-row-only, availability writes gated by `not shift_instance_week_is_published(...)`.
- **Atomic manager RPC pattern:** `SECURITY DEFINER`, `set search_path = public, pg_temp`, `perform assert_active_manager();`, `revoke execute … from public, anon; grant … to authenticated`. `#variable_conflict use_column` when a `RETURNS TABLE` column collides with a column name. PL/pgSQL `RAISE` uses bare `%`. **Write paths are closed to direct table writes** (`rota_assignments`, now `rota_publications`): the RPC is the only way.
- **"Today" is always the resort's operational date** (`operational_today`, Europe/Zurich), never `current_date`/the browser date.
- `audit_log.context jsonb` comes from a transaction-local `app.audit_context` set and cleared by the RPCs (never leaks into a later write).
- Custom SQLSTATEs: `VD001` (assign needs override), `VD002` (stale Auto-Rota plan), `VD003` (publish needs uncovered acknowledgement; DETAIL = count). Advisory locks: only `rota_week_lock`. Error contract pattern: `42501` not a manager, `P0002` not found, `22023` malformed, `55006` locked (DETAIL names it), `23514` rule violation (DETAIL where distinct), `23505` duplicate.
- Managers are global in V1 (no per-resort manager scope).
- Deployment policy: no hosted project; every migration only runs through a full local `supabase db reset`. Do a deployment-readiness review before the first persistent environment exists (`docs/db-testing.md`).

## K. Known limitations (all deliberate and documented)

- The manager **Dashboard** and **Payroll** page are still Stage 1.1 mock data (the Dashboard can show an uncovered Verbier Dinner while the live rota correctly shows no shifts). Not to be papered over by mixing real shifts into the mock pages.
- **No Attendance UI/workflow** (the `attendance` table and its guard on unassign exist in the DB; managers can currently write the table directly — it has not been through a PB-A-style RPC closure yet). No Onfleet integration, no payroll calculation, no Partner Payments module.
- **Publish Rota V1 scope:** publish-only (**no unpublish / retract / republish control**); no notifications and no auto-publish; no publication snapshot or history (drivers see live assignments); a published week can be edited manually and edits are not flagged; publishing does not require availability confirmation or full coverage (only the uncovered acknowledgement); the shared Modal's Close (X) button stays enabled during a pending publish but is ignored until the call finishes; the Availability detail query keys have no resort in them, so the post-publish refresh marks any cached same-week driver detail stale (harmless extra refetch).
- **Auto-Rota V1 scope:** no overlap protection, daily maximum or rest period (a driver may get several — even overlapping — shifts a day if Available for each); **fairness is per resort + week only**; **no bulk undo / clear / regenerate-from-scratch**; the planner is a greedy heuristic, not a global optimum.
- **No confirmation on Remove** in Manual Rota.
- **Mock revision-ID limitation:** a mock `reviseShift` that recreates a template changes mock instance ids, orphaning mock assignments.
- **Shared `rule_violation` SQLSTATE:** `23514` covers inactive driver / other resort / cancelled shift / over-long reason with no DETAIL in the assign RPC (mapped to one kind; distinct kinds need a new migration).
- **API `max_rows = 1000`:** the manager availability read returns shifts × drivers rows; page it before one resort-week could approach 1000.
- Driver My Rota refreshes on mount / week change / focus only (no push). Mock-mode My Rota reads "not published yet" until a publish.
- After a stale-data failure the manual assign dialog stays open (server message shown); Cancel closes it.
- Bundle-size warning (>500 kB) is cosmetic and pre-existing.
- **iCloud (recurring, real):** the project lives on `~/Desktop`; iCloud evicts `.git` objects, source files and `node_modules` files. Symptoms: `git checkout` hanging for minutes, vitest/tsc hanging, `ETIMEDOUT`, `ERR_INVALID_PACKAGE_CONFIG`, rollup "does not provide an export named VERSION" (a dataless file reads as empty). Check `find . -flags +dataless -type f | wc -l`; re-materialise with a parallel `cat`; for stubborn `node_modules` files run `npm ci` (local only). Never commit workarounds; moving the repo out of iCloud-synced storage is the user's call.
